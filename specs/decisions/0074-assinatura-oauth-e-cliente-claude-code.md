# 0074 — Assinatura OAuth, cliente Claude Code e verificação estrita do cliente no driver `anthropic`

Status: aceita (pedido do humano em 2026-11-03) nos itens 1–4; provisória nos itens 5–19 (gatilho de revisão em cada um)
Data: 2026-11-03
Atualiza: [0042](0042-fidelidade-total-ao-provedor-real.md) (exceção explícita do item 4: uma opção de driver que recusa clientes que o real aceitaria) e [0016](0016-diretorio-examples.md) (exemplo `claude-code-assinatura`, item 17)

## Contexto
O humano pediu, na sessão de 2026-11-03, três coisas para o driver `anthropic`: (1) a autenticação de conta de assinatura do Claude Code (OAuth, tokens `sk-ant-oat01-…`) funcionar no wwz; (2) um cliente de testes que se comporta exatamente como o Claude Code, com requisições byte a byte idênticas; (3) um modo ultra restrito em que o wwz recusa, com um erro que diz que o cliente está falsificando requisições, todo cliente que não se comporta como o Claude Code.

Fatos novos (2026-11-03, `tmp/claude-code/`, fora do git):
- **O wwz atual recusa o Claude Code 2.1.308.** Com `wwz serve` (driver `anthropic`) e `claude -p`: primeiro `400 messages.1.output_config: Extra inputs are not permitted` (o cliente tira o beta `per-turn-control-2026-07-01` e reenvia) e depois `400 messages.1.role: Input should be 'user' or 'assistant'`, falha definitiva. O real aceita `role: "system"` em `messages`: a fixture já gravada `testdata/real/anthropic/validation/a3_badrole_second.json` traz o texto real `Allowed roles are "user", "assistant" or "system"`, e o Claude Code em produção manda essa forma. A recusa do wwz é desvio do real (ADR 0042), não regra nova; o resto da forma (`output_config` por mensagem, `thinking.display`, `context_management`, `safeguards`, `defer_loading`, `cache_control.ttl`) fica a conferir no real com a chave de API do projeto.
- **Capturas byte a byte do Claude Code 2.1.308** (`tmp/claude-code/captures/`, servidor TCP `capture.py`, `env -i`, `CLAUDE_CONFIG_DIR` vazio): linha `POST /v1/messages?beta=true HTTP/1.1`, ordem e grafia exatas dos headers, corpo compacto de `JSON.stringify`, billing header em `system[0]`, fingerprint, `metadata.user_id`, betas por tipo de requisição (análise em `tmp/claude-code/FINDINGS.md`).
- **Formas OAuth tiradas do binário** (`tmp/claude-code/oauth-shapes.md`): token endpoint em JSON, campos do perfil (`account.uuid`, `account.email`, `organization.uuid`, `organization_type`, `rate_limit_tier`), `request-id` obrigatório no perfil, headers `anthropic-ratelimit-unified-*` e quando o Claude Code não retenta um 429.
- **Real conferido sem credencial** (`tmp/claude-code/real-probes/`): `GET|HEAD /api/hello` → 200 `{"message": "hello"}`; `GET /v1/oauth/hello` → 200 `{"message":"hello"}`, `HEAD` → 405; Bearer `sk-ant-oat01-invalid` em `/v1/messages` e em `/api/oauth/profile` → 401 `authentication_error` `OAuth access token is invalid.` com `request-id`, `x-should-retry: false` e `cache-control: no-store`.
- O `/login` do Claude Code real **nunca chega ao wwz**: `CLAUDE_CODE_CUSTOM_OAUTH_URL` só aceita uma allowlist fixa, e as rotas de conta e OAuth usam o host fixo `api.anthropic.com`/`platform.claude.com`. Só `/v1/messages` (e a sonda `HEAD /api/hello`, capturada) seguem `ANTHROPIC_BASE_URL`. O Claude Code real usa o wwz com `ANTHROPIC_BASE_URL=<wwz>` e `CLAUDE_CODE_OAUTH_TOKEN=<access token emitido pelo wwz>`.

## Decisão

**Decididos pelo humano (2026-11-03).**
1. O driver `anthropic` aceita a autenticação de assinatura do Claude Code (OAuth): emite e aceita tokens `sk-ant-oat01-…`/`sk-ant-ort01-…`, serve as rotas OAuth e de conta, e responde à inferência de assinante como o real (spec 006, 16.2.1).
2. Há um cliente de testes que se comporta como o Claude Code, com requisições byte a byte idênticas às do Claude Code 2.1.308: `wwz-load claude-code` (spec 015) sobre o perfil `internal/claudecode` (spec 020).
3. Há um modo ultra restrito no driver `anthropic` que recusa, com erro próprio que diz que o cliente falsifica requisições, todo cliente que não se comporta exatamente como o Claude Code (spec 020).
4. **Exceção à ADR 0042.** O modo do item 3 é a opção `drivers[].options.client_verification` (`off` padrão, `claude-code`). Com `off` o driver é o real. Com `claude-code` o wwz recusa clientes que o real talvez aceitasse: é um desvio pedido pelo humano e opt-in por montagem, no espírito de "o real também atesta o cliente" (billing header, `cch`, credencial "only authorized for use with Claude Code"), não uma volta do `server.strict` (ADR 0029, removido pela 0042), que validava campos do corpo para todos os drivers. Nenhuma outra opção de driver pode divergir do real.

**Escolhidos na implementação (provisórios).**
5. **Recusa do modo estrito.** HTTP **403**, `content-type: application/json`, corpo `{"type":"error","error":{"type":"forged_request_error","message":"Client verification failed: this request does not match Claude Code <versões>; the client is forging Claude Code requests (<reason>: <detalhe>)."},"request_id":"req_…"}`, headers `request-id`, `x-should-retry: false` e `x-wwz-client-verification: failed; reason=<reason>`. O tipo `forged_request_error` não existe no real (403 do real é `permission_error`); é escolha do wwz para o roteador sob teste distinguir a recusa. Gatilho: o humano preferir um 403 `permission_error` com outro texto, ou um envelope real de atestação de cliente aparecer.
6. **Códigos `reason` estáveis**, um por recusa, na ordem de checagem da spec 020: `query`, `transfer_encoding`, `header_missing`, `header_order`, `user_agent`, `unknown_version`, `header_value`, `beta`, `body_encoding`, `body_key_order`, `metadata`, `session_mismatch`, `billing_header`, `fingerprint`, `identity`. Lista fechada: código novo é mudança de contrato (spec 020). Gatilho: uma recusa que não cabe em nenhum código.
7. **Onde a verificação entra.** Só nas rotas de inferência (`POST /v1/messages`, `POST /v1/messages/count_tokens`) da montagem com `claude-code`, como **primeiro passo**, antes da credencial, do corpo e dos limites (a ordem da ADR 0053 vale depois dela). A recusa não consome cota, não conta em limite nem em abuso. `/v1/models`, rotas OAuth e de conta e `/api/hello` não são verificadas. Gatilho: o roteador sob teste precisar de 401 antes do 403.
8. **Tokens sem estado.** Como o Console do `opencode` ([ADR 0072](0072-recursos-do-opencode-ai-no-driver-opencode.md), item 17): access token, refresh token e authorization code são assinados com HMAC-SHA256, tendo como segredo o valor da entrada de `keys[]` cujo label é `drivers[].options.oauth_key`. O token representa essa chave (conta, projeto, tier, limites e cota). Nada no store; o code não é de uso único (sem estado não se detecta reuso). Layout e tempos na spec 006, 16.2.1. Gatilho: o roteador sob teste depender de revogação ou de code de uso único.
9. **Plano por opção.** `drivers[].options.oauth_plan` ∈ `pro`, `max_5x`, `max_20x`, `team`, `enterprise` (padrão `max_5x`) define `organization_type` e `rate_limit_tier` do perfil e do bootstrap. Os limites da assinatura são o `quota_usd` (5 h e semana) da conta da chave, que o wwz já tem (exemplo `cota-5h-semana`); o plano não muda limite nenhum sozinho. Gatilho: valores reais de `rate_limit_tier` para `pro`/`team`/`enterprise` (só os dois do Max aparecem no binário).
10. **Headers `anthropic-ratelimit-unified-*`** saem nas respostas de inferência autenticadas por token OAuth, no lugar dos `anthropic-ratelimit-{requests,tokens,input-tokens,output-tokens}-*`, calculados do `quota_usd` da conta (utilização = gasto da janela ÷ cota da janela). Nomes do binário; valores, ordem e presença não conferidos (spec 006, 16.2.1). Gatilho: uma resposta real de assinante (só com token do humano, que não é usado).
11. **O que não é reproduzido sem conferência.** A recusa real "This credential is only authorized for use with Claude Code and cannot be used for other API requests." (relato público) não sai no modo `off`: a regra que a dispara é desconhecida. Fica "não conferido" na spec 006, seção "Não conferidos no real". Gatilho: observação do real com um token de assinatura.
12. **Cliente recusa hosts reais.** `wwz-load claude-code` recusa `--target` em `anthropic.com`, `claude.ai`, `claude.com` e subdomínios (código 2), nunca segue redirect para outro host e não lê credenciais do Claude Code instalado. É um cliente do simulador, não um meio de usar credencial de assinatura fora do Claude Code. Gatilho: nenhum (regra de uso).
13. **Nada do prompt padrão do Claude Code no git.** As fixtures `testdata/real/claude-code/2.1.308/` são só as capturas mínimas (`--system-prompt` próprio, sem tools; as de `count_tokens`, 013 e 014, com `--tools Read`, cujo corpo leva `tools: []` e o arquivo lido, sem descrições de tools do Claude Code), com o diretório de trabalho trocado por `/work`, a configuração por `/cfg`, o diretório de scratchpad do bloco de ambiente (derivado do diretório de trabalho e da sessão, com o nome do usuário) por `/private/tmp/claude-501/-work/<sessão>/scratchpad`, a home por `/home/user`, o usuário por `user` e o `Content-Length` recalculado (revisão da task 452). A captura completa (`full-default-oauth.raw`, 45 KB de prompt e tools) e a do título (011, prompt de título) ficam em `tmp/`. O bloco de ambiente (`role: "system"` em `messages`) entra porque o Claude Code o manda mesmo com `--system-prompt` e a identidade byte a byte depende dele. Gatilho: o humano pedir outra política.
14. **Achado além do FINDINGS.** O turno principal interativo (captura 012) traz a chave de topo `safeguards` (`[{"type":"dangerous_tool_use","classifier_context":{…}}]`, com caminhos, home e nome do usuário) e `thinking.display: "updates"`; a ordem das chaves desse tipo é `model, messages, system, tools, metadata, max_tokens, thinking, context_management, safeguards, output_config, stream`. Entra no perfil e na validação a conferir.
15. **Proxy.** O modo estrito exige que os headers cheguem como o cliente os mandou. Um proxy que canoniza nomes ou acrescenta headers (Traefik, Go `net/http`) faz toda requisição ser recusada (`header_order`); em produção, só nas portas diretas. Gatilho: necessidade de verificar atrás de proxy (lista de headers de proxy ignorados).
16. **Perfil por versão.** Só a 2.1.308 entra agora; versão de outro Claude Code → `unknown_version`. Versão nova entra por tarefa, com captura nova. Gatilho: o humano atualizar o Claude Code.
17. **Exemplo.** `examples/claude-code-assinatura/` (índice 17, porta 18117) entra na lista da ADR 0016 (18 exemplos), com smoke: login pelo cliente, `ask`, recusa de um SDK oficial com `forged_request_error`.
18. **Uso normal do Claude Code no modo estrito** (revisão da task 464, achados da task 457). Fato novo: com o prompt e as tools padrão, o Claude Code 2.1.308 real era recusado (`fingerprint`) e manda formas que as capturas mínimas não tinham; cada uma foi conferida no tráfego real (15 modos de `tests/claudecode/default-mode.sh`) e nas strings do binário. O `Verify` aceita: o fingerprint de qualquer bloco `text` da primeira mensagem `user` (os blocos meta vêm antes do prompt e nem sempre têm tag); `inline-tools-2026-09-15` e `advisor-tool-2026-03-01` presentes ou ausentes (flags do Claude Code, com qualquer credencial); `extended-cache-ttl-2025-04-11` ausente com OAuth (subagente, overage), com o `cache_control` de `system[1]` sem `ttl`; o subagente (`x-claude-code-agent-id` e `x-claude-code-parent-agent-id` depois de `x-app`, ` cc_is_subagent=true;` no billing header, um sem o outro é `billing_header`); o turno depois de um resultado de tool com os betas de `turn_safeguards`; e o tipo `classifier` (classificador do modo auto: não-stream, `X-Stainless-Timeout: 60`, beta `context-1m-2025-08-07`, `system[1]` com o prompt do classificador, que o perfil não gera). A lista de `reason` não muda; as mutações da spec 020 seguem recusadas com o mesmo código. Detalhe na spec 020. Gatilho: nova versão do Claude Code (captura nova, item 16) ou uma recusa nova com o Claude Code real em uso normal.
19. **Porta 8008 para o modo estrito em produção** (task 468; decisão do humano em 2026-11-03). Fato novo do deploy em produção: no servidor do autor, a 8004 do haproxy `wwz-ports` divide a porta com outro serviço do host em `mode http` (com `option forwardfor`). Em `mode http` o haproxy tira o hop-by-hop `Connection` e acrescenta `X-Forwarded-For`, e o mount estrito `/claude-code` da 8004 recusa até o `wwz-load claude-code` (`header_missing: Connection`); direto no container ele aceita. Decisão: a **porta 8008** do IP público do servidor vai em `mode tcp` para a instância `wwz-anthropic` (`198.18.128.15:8000`), só para o modo estrito; a 8004 continua para o modo `off`. As portas diretas passam a ser 8000–8008 (anota a ADR 0017 sem reescrevê-la) e o smoke externo cobre a 8008 com o `wwz-load claude-code` (specs 019 e 020). O haproxy real do servidor fica em `autor/haproxy.cfg`, fora do git ([ADR 0076](0076-dados-do-autor-fora-do-git.md)); o versionado é o genérico, todo em `mode tcp`. O item 15 continua: atrás de proxy L7 o modo estrito recusa todo cliente. Gatilho: a 8004 voltar a `mode tcp` ou o modo estrito passar a tolerar headers de proxy.

## Alternativas consideradas
- Atestar o cliente por um header secreto ou pelo `cch` do first-party: não exercita o roteador sob teste com o tráfego real do Claude Code (recusado).
- Guardar tokens e codes no store: dá revogação e uso único, mas acrescenta escrita no caminho de autenticação; o padrão já aceito no `opencode` é sem estado.
- `net/http` no cliente: canoniza e reordena headers; não dá identidade byte a byte.
